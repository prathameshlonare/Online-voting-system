> **Goal:** By the end of this session, you'll be able to define, run, and manage multi-container applications with a single file. You'll build a working `docker-compose.yml` that launches your Online-voting-system frontend and backend together.

## Part 1: Why This Matters for Online-voting-system (10 min)

Yesterday you containerized the React frontend of Online-voting-system with a single Dockerfile. That works for one container. But real applications aren't one container.

Your Online-voting-system needs:
- A React frontend (port 3000)
- A mock backend API (simulating Lambda responses)
- A DynamoDB local instance (for local testing)

That's three containers. Without Docker Compose, you'd run three separate `docker run` commands with manually linked networks, volumes, and environment variables. One typo and something breaks.

Docker Compose lets you define all three in one YAML file and launch everything with one command.

| Command/Concept | What it does | When I'd use it |
|-----------------|--------------|-----------------|
| `docker-compose.yml` | Declares all services, networks, volumes | Every multi-container project |
| `docker compose up` | Starts all services defined in the file | Daily development workflow |
| `docker compose down` | Stops and removes all containers + networks | End of work session |
| `docker compose logs` | Shows output from all services | Debugging service communication |
| `docker compose exec` | Runs a command inside a running container | Testing or inspecting a service |
| `depends_on` | Controls startup order | Frontend needs backend to be ready |

## Part 2: The Problem — Running 3 Containers Manually (20 min)

### The Problem

Yesterday you ran your frontend with:
```bash
docker run -p 3000:3000 voting-app
```

That's one command for one container. Now imagine you need three:

```bash
# Terminal 1: Start DynamoDB Local
docker run -p 8000:8000 amazon/dynamodb-local

# Terminal 2: Start mock backend
docker run -p 4000:4000 --link dynamodb voting-backend

# Terminal 3: Start frontend
docker run -p 3000:3000 --link backend voting-app
```

Three terminals. Three commands. If DynamoDB starts late, the backend crashes. If you forget `--link`, the frontend can't reach the backend. If you kill the wrong terminal, half your app goes down.

This is exactly the problem Docker Compose solves.

### The Command

The Docker Compose file replaces those three commands with a single YAML declaration:

```yaml
# docker-compose.yml
version: '3.8'

services:
  frontend:
    build:
      context: .
      dockerfile: Dockerfile.frontend
    ports:
      - "3000:3000"
    depends_on:
      - backend

  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile
    ports:
      - "4000:4000"
    depends_on:
      - dynamodb

  dynamodb:
    image: amazon/dynamodb-local
    ports:
      - "8000:8000"
```

Let's break it down:
- `version: '3.8'` — Compose file format version (use 3.8 for most projects)
- `services:` — defines each container as a named service
- `build:` — tells Compose to build an image from a Dockerfile (instead of pulling from a registry)
- `context: .` — the build context directory
- `ports:` — maps host port to container port (host:container)
- `depends_on:` — ensures this service starts AFTER the listed service
- `image:` — uses a pre-built image from Docker Hub (no Dockerfile needed)

### Try It Now

Create the compose file for your Online-voting-system:

```bash
cd ~/Online-voting-system
nano docker-compose.yml
```

Paste the YAML above, save, then:

```bash
docker compose up
```

You'll see output like:

```
[+] Running 3/3
 ✔ Container voting-dynamodb-1    Started    0.8s
 ✔ Container voting-backend-1     Started    1.2s
 ✔ Container voting-frontend-1    Started    0.6s
```

All three containers started. One command. No terminal juggling.

### What This Tells You

| Line | Meaning |
|------|---------|
| `[+] Running 3/3` | 3 services defined, 3 started successfully |
| `Started 0.8s` | How long it took to start each container |
| No errors | All dependencies resolved, ports available |

## Part 3: Managing Services — Up, Down, Logs, Exec (20 min)

### The Problem

You started everything with `docker compose up`. Now what? How do you stop it? How do you check what's happening inside a container? How do you restart just one service?

Running containers in the background without management tools is like starting a car and never checking the mirrors.

### The Commands

**Stop everything:**
```bash
docker compose down
```

Output:
```
[+] Running 3/3
 ✔ Container voting-frontend-1    Removed    0.5s
 ✔ Container voting-backend-1     Removed    0.4s
 ✔ Container voting-dynamodb-1    Removed    0.3s
```

**Run in background (detached mode):**
```bash
docker compose up -d
```

The `-d` flag runs containers in the background. You get your terminal back.

**Check logs:**
```bash
docker compose logs
```

This shows ALL logs from ALL services. To watch them live:
```bash
docker compose logs -f
```

To see logs from just one service:
```bash
docker compose logs frontend
```

**Execute a command inside a running container:**
```bash
docker compose exec backend sh
```

This drops you into a shell inside the backend container. Now you can:
```bash
ls /app
curl http://localhost:8000
exit
```

**Restart just one service:**
```bash
docker compose restart frontend
```

### Try It Now

```bash
# Start in background
docker compose up -d

# Check what's running
docker compose ps

# Watch all logs
docker compose logs -f

# Press Ctrl+C to stop watching

# Execute into backend
docker compose exec backend sh

# You're now inside the backend container
ls /app
exit

# Restart just the frontend
docker compose restart frontend

# Stop everything
docker compose down
```

### What This Tells You

| Command | Use It When |
|---------|-------------|
| `docker compose up -d` | Start and forget (background mode) |
| `docker compose down` | Clean stop, remove everything |
| `docker compose logs -f` | Debugging — see what's happening live |
| `docker compose exec` | Inspect or debug a specific container |
| `docker compose restart` | One service crashed, restart it alone |
| `docker compose ps` | Quick status check of all services |

2. Run `docker compose ps` — verify all show "Up" status
3. Run `docker compose logs frontend` — see frontend output
4. Run `docker compose exec backend sh` — drop into backend shell
5. Run `docker compose down` — clean shutdown

## Part 4: Environment Variables and Networking (15 min)

### The Problem

Your backend needs to connect to DynamoDB. In production, it uses `http://localhost:8000`. But in Docker, `localhost` inside one container refers to THAT container, not the host or other containers.

Docker Compose creates a network for your services. Instead of `localhost`, services find each other by their service name:

```
backend → http://dynamodb:8000
frontend → http://backend:4000
```

### The Commands

**Environment variables in compose:**

```yaml
services:
  backend:
    build: ./backend
    ports:
      - "4000:4000"
    environment:
      - DYNAMODB_ENDPOINT=http://dynamodb:8000
      - AWS_REGION=us-east-1
      - NODE_ENV=development
    depends_on:
      - dynamodb
```

- `environment:` — sets env vars inside the container
- Use `KEY=VALUE` format (no quotes needed for simple values)
- Access them in code: `process.env.DYNAMODB_ENDPOINT`

**Using an .env file (cleaner):**

Create `.env` in the same directory as `docker-compose.yml`:
```bash
DYNAMODB_ENDPOINT=http://dynamodb:8000
AWS_REGION=us-east-1
NODE_ENV=development
```

Reference in compose:
```yaml
services:
  backend:
    env_file:
      - .env
```

**Custom networks (explicit control):**

```yaml
services:
  frontend:
    build: .
    ports:
      - "3000:3000"
    networks:
      - app-network

  backend:
    build: ./backend
    networks:
      - app-network

  dynamodb:
    image: amazon/dynamodb-local
    networks:
      - app-network

networks:
  app-network:
    driver: bridge
```

By default, all services in a compose file share a network. But explicit networks let you isolate services — e.g., frontend can't talk to DynamoDB directly.

### Try It Now

Add environment variables to your compose file:

```yaml
services:
  backend:
    build: ./backend
    ports:
      - "4000:4000"
    environment:
      - DYNAMODB_ENDPOINT=http://dynamodb:8000
      - AWS_REGION=us-east-1
    depends_on:
      - dynamodb
```

Start services:
```bash
docker compose up -d
docker compose exec backend env | grep DYNAMODB
```

You'll see:
```
DYNAMODB_ENDPOINT=http://dynamodb:8000
```

## Part 5: Build Task — Complete docker-compose.yml (30 min)

Now combine everything into a complete, working compose file for your Online-voting-system.

### Create the File

```bash
cd ~/Online-voting-system
nano docker-compose.yml
```

### Write This Script

```yaml
version: '3.8'

services:
  # React Frontend — port 3000
  frontend:
    build:
      context: .
      dockerfile: Dockerfile.frontend
    ports:
      - "3000:3000"
    environment:
      - REACT_APP_API_URL=http://localhost:4000
    depends_on:
      - backend
    networks:
      - voting-network

  # Mock Backend — simulates Lambda + API Gateway
  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile
    ports:
      - "4000:4000"
    environment:
      - DYNAMODB_ENDPOINT=http://dynamodb:8000
      - AWS_REGION=us-east-1
      - AWS_ACCESS_KEY_ID=local
      - AWS_SECRET_ACCESS_KEY=local
    depends_on:
      - dynamodb
    networks:
      - voting-network

  # DynamoDB Local — for local testing
  dynamodb:
    image: amazon/dynamodb-local
    ports:
      - "8000:8000"
    command: "-jar DynamoDBLocal.jar -sharedDb -inMemory"
    networks:
      - voting-network

networks:
  voting-network:
    driver: bridge
```

### Make Sure Backend Dockerfile Exists

If you haven't created `backend/Dockerfile` yet:

```bash
mkdir -p backend
nano backend/Dockerfile
```

```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
EXPOSE 4000
CMD ["node", "server.js"]
```

### Create a Simple Backend

If `backend/server.js` doesn't exist:

```bash
nano backend/server.js
```

```javascript
const http = require('http');
const port = 4000;

const server = http.createServer((req, res) => {
  res.setHeader('Access-Control-Allow-Origin', '*');
  res.setHeader('Access-Control-Allow-Methods', 'GET, POST, OPTIONS');
  res.setHeader('Access-Control-Allow-Headers', 'Content-Type');

  if (req.method === 'OPTIONS') {
    res.writeHead(200);
    res.end();
    return;
  }

  if (req.url === '/api/health') {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ status: 'ok', service: 'voting-backend' }));
    return;
  }

  res.writeHead(404, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({ error: 'not found' }));
});

server.listen(port, () => {
  console.log(`Backend running on port ${port}`);
});
```

```bash
nano backend/package.json
```

```json
{
  "name": "voting-backend",
  "version": "1.0.0",
  "scripts": {
    "start": "node server.js"
  }
}
```

### What You Just Built

You now have a complete multi-container setup for your Online-voting-system:
- **1 file** (`docker-compose.yml`) defines everything
- **1 command** (`docker compose up`) starts 3 services
- **1 command** (`docker compose down`) stops everything cleanly
- Services communicate by name, not by IP or `localhost`
- Environment variables are injected automatically

This is exactly how production apps work — multiple services, defined as code, managed together.

## Part 6: Recap (5 min)

### What You Learned

| Command | Use Case | My Project |
|---------|----------|------------|
| `docker compose up -d` | Start all services in background | Launch Online-voting-system locally |
| `docker compose down` | Stop and clean up | End work session |
| `docker compose logs -f` | Debug live | See what's failing in backend |
| `docker compose exec` | Inspect a container | Test API endpoints inside backend |
| `docker compose restart` | Restart one service | Fix a crashed frontend |
| `docker compose ps` | Check status | Verify all services running |
| `depends_on` | Startup ordering | Frontend waits for backend |
| `environment` / `env_file` | Inject config | DynamoDB endpoint, AWS keys |
| `networks` | Service isolation | Frontend can't access DynamoDB directly |

### The Pattern

When setting up a multi-container app, do these steps in order:

1. **List your services** — What containers does your app need? (frontend, backend, database)
2. **Define each service** — Dockerfile or image, ports, environment variables
3. **Add depends_on** — Which service needs which to start first?
4. **Create a network** — Let services find each other by name
5. **Test with `docker compose up`** — Watch logs, verify all start
6. **Test communication** — exec into frontend, curl the backend service name
7. **Clean up with `docker compose down`** — Verify clean shutdown
