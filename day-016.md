## Part 2: Docker Compose — One File, Full Stack (20 min)

### The Problem

Before: 3 terminals, 3 `docker run` commands, manual `--link`, 10 min startup, 1 typo = broken app.

### The Fix

**docker/docker-compose.yml**
```yaml
version: '3.8'
services:
  frontend:
    build:
      context: ../frontend
      dockerfile: ../docker/Dockerfile.frontend
    ports: ["3000:3000"]
    networks: [frontend-net]
    depends_on: [backend]

  backend:
    build:
      context: ../backend
      dockerfile: ../docker/Dockerfile.backend
    ports: ["4000:4000"]
    networks: [frontend-net, backend-net]
    depends_on: [dynamodb]

  dynamodb:
    image: amazon/dynamodb-local
    ports: ["8000:8000"]
    networks: [backend-net]
    volumes: [voting-db-data]

networks:
  frontend-net:  # public subnet equivalent
  backend-net:   # private subnet equivalent

volumes:
  voting-db-data:
```

### Try It Now

```bash
cd Online-voting-system
docker compose -f docker/docker-compose.yml up -d
# 3 services start in 2 seconds
```

### Exercise 1

1. Run `docker compose ps` — verify all 3 healthy
2. Run `docker network ls` — verify `frontend-net` and `backend-net`
3. Test: `curl http://localhost:3000` → should load frontend

## Part 3: Network Isolation — VPC Pattern in Compose (20 min)

### The Problem

Frontend could reach DynamoDB directly. In production, that's a security violation (public subnet → database).

### The Fix

Two custom bridge networks mirror VPC public/private subnets:

```
frontend-net (public)     backend-net (private)
┌──────────────┐          ┌──────────────┐
│  frontend    │ ◄─────── │   backend    │ ◄─────── │ dynamodb │
└──────────────┘          └──────────────┘
      │                         │
   Internet                  Internal only
```

### Try It Now

```bash
# Frontend CANNOT reach dynamodb (no shared network)
docker exec voting-frontend-1 nslookup dynamodb
# ** connection timed out ** (correct!)

# Frontend CAN reach backend
docker exec voting-frontend-1 nslookup backend
# ** resolves to private IP ** (correct!)

# Backend CAN reach dynamodb
docker exec voting-backend-1 nslookup dynamodb
# ** resolves to private IP ** (correct!)
```

### Exercise 2

1. Add a 4th service `redis` to `backend-net` only
2. Verify frontend cannot resolve `redis`
3. Verify backend can resolve `redis`

## Part 4: Persistent Volumes — Data Survives Restart (15 min)

### The Problem

`docker compose down` destroyed all votes. Not acceptable.

### The Fix

Named volume `voting-db-data` mounted to DynamoDB:

```yaml
services:
  dynamodb:
    volumes: [voting-db-data]
volumes:
  voting-db-data:
```

### Try It Now

```bash
# Add 10 votes via frontend
docker compose down          # no -v flag!
docker compose up -d
# Votes still there ✓

# Nuclear option (removes volume):
docker compose down -v       # votes GONE
```

### Exercise 3

1. Inspect volume: `docker volume inspect voting-db-data`
2. Find mountpoint on host: `docker volume inspect voting-db-data --format '{{.Mountpoint}}'`
3. Verify data files exist there

## Part 5: Multi-Stage Dockerfile — 1.4GB → 23MB (30 min)

### Before (One-Stage)

```dockerfile
FROM node:18
COPY . .
RUN npm install
RUN npm run build
CMD ["npm", "start"]
# Result: 1.42GB, root user, 2 min rebuilds
```

### After (Multi-Stage)

**docker/Dockerfile.frontend.prod**
```dockerfile
# Stage 1: Build
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: Runtime
FROM nginx:alpine
RUN adduser -S appuser
COPY --from=builder /app/build /usr/share/nginx/html
USER appuser
# Result: 23MB, non-root, 15 sec rebuilds (layer caching)
```

### Key Patterns

| Pattern | Why It Matters |
|---------|----------------|
| `COPY package*.json` first | Layer cache — only rebuild on dependency change |
| `npm ci` not `npm install` | Deterministic, faster, fails on mismatch |
| `nginx:alpine` base | 23MB vs 1.2GB node image |
| `adduser -S appuser` | Non-root = security best practice |
| `USER appuser` | Container runs unprivileged |

### Try It Now

```bash
cd Online-voting-system
docker build -t voting-frontend:optimized -f docker/Dockerfile.frontend.prod .
docker images voting-frontend:optimized
# Should show ~23MB

docker run -d -p 3000:80 voting-frontend:optimized
curl http://localhost:3000
# Should load frontend
```

## Part 7: Recap (5 min)

### What You Learned

| Command/Concept | Use Case | My Project |
|-----------------|----------|------------|
| `docker compose up -d` | Start full stack | Daily dev |
| Custom networks | Security isolation | VPC pattern |
| Named volumes | Data persistence | EBS/EFS equivalent |
| Multi-stage builds | Small, secure images | Production deploy |
| `npm ci` + package.json first | Layer caching | Fast CI/CD |

### The Pattern

When containerizing a multi-service app:
1. **Write Dockerfiles** — one per service, multi-stage for prod
2. **Define compose.yml** — services, networks, volumes
3. **Add network isolation** — frontend-net (public) → backend-net (private)
4. **Add persistence** — named volumes for databases
5. **Test `down`/`up` cycle** — verify data survives
6. **Push to GitHub** — `docker/` folder with prod compose
